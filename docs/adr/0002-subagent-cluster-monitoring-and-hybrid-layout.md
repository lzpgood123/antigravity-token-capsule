# ADR 0002: 子智能体集群监控架构与双模态布局 (Subagent Cluster Monitoring & Hybrid Layout)

## Status

Accepted

## Context

在复杂的多代理研发与代码审查场景中，Google Antigravity 会在主会话中动态派发多个独立子智能体（Subagents，如 Explorer、Coder、Reviewer）。这些 Subagent 拥有各自独立的全局唯一 UUID，在底层各自对应独立的 SQLite 数据库文件与上下文，不挤占主会话自身的 256k 物理上下文窗口。

然而，原有的 Token Capsule 仅监控单一活跃会话，存在两个核心局限：
1. **全局算力盲区**：无法统计由当前会话衍生出的子智能体所消耗的大量 Token 与财务折算费用。
2. **布局形态权衡**：用户在不同场景下对桌面占用有着冲突的诉求——日常编码时希望窗口极小（320px 紧凑单卡），但在多智能体并发压测或长时间任务中，又渴望一眼纵览全貌（免点击切换的双翼雷达）。

## Decision

我们确立了 **分层解耦数据模型 + 双模态混合布局（Tab + Dual-Wing）** 架构：

1. **分立上下文与财务双口径解耦 (Decoupled Scope & Dual Cost)**：
   * **物理上下文解耦**：顶部药丸与主卡片顶部的 256k 进度条严格反映主会话自身的物理窗口占用，杜绝将 Subagent 强行混入导致百分比失真。
   * **双费用透明联动**：主会话底部明确标明 `累计折算费用: $X.XXX (含集群: $Y.YYY)`，实现一目了然的防超支预警。
2. **轻量增量双向嗅探 (Incremental Mtime Sniffing)**：
   * `data_engine.py` 监听主会话的 `transcript.jsonl`，毫秒级提取当前会话派生出的所有子智能体 UUID、语义化角色名与状态（运行中 / 已完成）。
   * 建立多文件增量轮询池，通过读取各 Subagent 的 `.db-wal` 文件的 `mtime` 和大小变动，有更新时才只读触发解码，保证 CPU 占用率趋近于 0%。
3. **双模态呈现与托盘实时热切 (Hybrid Layout Modes)**：
   * **默认模式：方案 A（紧凑单卡 Tab + 折叠手风琴）**：卡片宽度保持 320px，通过顶部 `[ 主会话 ]` / `[ 智能体集群 •N ]` 切换。集群页提供微型仪表盘大盘条，点击子智能体可就地平滑展开详细指标（输入、输出、思考、耗时、速度）。
   * **扩展模式：方案 C（旁置双翼 / 实时雷达）**：卡片水平展为左右双翼（左为主会话，右为集群雷达），双屏全景展示。
   * **系统托盘集成**：系统右下角小图标右键菜单新增 **「📐 布局风格 (Layout Mode)」** 子菜单，支持在「紧凑单卡」与「展开双翼」之间一键热切，并将偏好持久化保存在配置文件中。

## Consequences

- **Positive**：
  * **兼顾灵巧与大盘**：完美满足用户既爱紧凑 Tab 又爱全景雷达的双重诉求，自由切换，不增加桌面干扰。
  * **全生命周期清晰**：运行中（呼吸绿灯）与已结束（静止灰灯）区分鲜明，便于成本复盘。
  * **零侵入高保真**：完全基于 Chromium/SQLite 本地机制，不篡改 Antigravity 核心。
- **Trade-offs**：
  * 双翼模式需要更多的桌面横向空间（约 680px）；在屏幕极窄场景下，系统托盘默认优先保持单卡模式。
